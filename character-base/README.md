# Gamboligy character base (humanoid template v1)

A reusable, rigged, **blank** stylized adult humanoid for the slot-game pipeline:

```
blank master ─► adjust proportions ─► freeze geometry + UVs ─► project artwork ─► bake texture
             ─► save as a new character (GLB + JSON) ─► animate with the existing rig / clips
```

Everything here is generated by code (Blender 4.2 + Python for authoring, Three.js for preview/validation),
so the base can be rebuilt, versioned and extended instead of repaired per game.

> This project is self-contained in `character-base/`. It does not touch any slot-game code. It lives in this
> repository only because it was the repository available to the session — it can be moved as-is to its own repo.

## Quick start

```bash
# authoring (Blender 4.2 as a Python module; a Blender 4.2 install also works: see below)
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python tools/build.py all        # layout (if missing) → master → freeze → stocky → freeze → diag texture

# viewer / references / validation
npm install                                 # three + playwright-core (Chromium is used headless)
npm run viewer                              # http://localhost:8765/viewer/
npm run refs                                # projection references for all characters
npm run validate                            # fresh-instance validation + validation/REPORT.md
```

With a regular Blender install instead of the pip module:
`blender --background --python tools/build.py -- all` (same sub-commands after `--`).

The viewer only needs a static file server (`viewer/vendor/` contains the pinned three.js 0.180 files).
`node scripts/build-artifact.mjs <outDir>` produces a single-page hosted copy (three.js from jsDelivr, GLBs shipped
as base64 text); in that version Export keeps the GLB in memory and *Reload* rebuilds the character from those bytes.

## Conventions

* **Units** metres. **GLB/Three.js space**: +Y up, the character faces **+Z**, **character's left = +X**.
  Authoring (Blender) is +Z up / faces −Y; the exporter converts. L/R are always from the character's perspective.
* **Bones**: local +Y runs head→tail. Local +Z is the bone's positive bend direction, so a positive rotation
  about local +X is flexion/curl (the exact meaning per bone group is in `skeleton.bendConvention` in every JSON).
  The hand's local +Z is the palm normal; fingers curl about +X.
* **Rest pose** = relaxed A-pose (arms 48° below horizontal, 14° elbow bend, palms facing the thighs, thumbs
  forward, fingers lightly relaxed, feet 6° toe-out). This is the bind pose stored in the GLB.
* **Skin**: max 4 influences, normalised. Weights are computed on the unified surface before the split, so both
  copies of a boundary vertex always have identical weights, positions and normals.

### Body parts (separately named & selectable)
`Head, Neck, Torso, Pelvis, UpperArm_L/R, Forearm_L/R, Hand_L/R, Thigh_L/R, Shin_L/R, Foot_L/R`

Parts are face sets of **one continuous subdivision surface**; boundaries are shared edge loops (armhole,
elbow, wrist, neck base, jaw line, waist, leg openings, knee, ankle). They are exported as separate skinned
meshes on one skeleton. No part relies on hidden intersections.

### Skeleton
`root → pelvis → spine_01 → spine_02 → chest → neck → head`, `clavicle_L/R → upperarm → forearm → hand →
thumb_01..03 / index|middle|ring|pinky_01..03`, `forearm_twist_L/R`, `thigh → shin → foot → toe`.

**Driven helper joints** (production trick against linear-blend-skinning collapse) —
`shoulder_helper_*, elbow_helper_*, hip_helper_*, knee_helper_*` take exactly **half** of their source joint's
rotation; `forearm_twist_*` takes half of the hand's twist. Blended vertices at those joints are routed through
the helper, so deep bends keep volume. Rules (also in the JSON `skeleton.driverRules`):

* `half`: `helper.basis = slerp(identity, source.basis, 0.5)` (helper shares the source's rest frame)
* `twist_half`: `helper.basis = rotY(0.5 · swing-twist angle of source.basis about +Y)`

They are **baked into every clip**, and the viewer applies them after any manual posing. A runtime that poses
bones procedurally (its own IK) must apply the same two rules.

### Attachment sockets (glTF nodes parented to bones)
| node | parent | frame |
|---|---|---|
| `socket_hand_L_prop` / `socket_hand_R_prop` | `hand_L` / `hand_R` | origin = centre of a closed power grip (Ø32 mm handle); **+Y** = grip axis exiting the thumb side; **+Z** = out of the palm |
| `socket_head_accessory` | `head` | origin at the crown; +Y up, +Z forward |
| `socket_back_accessory` | `chest` | on the skin between the shoulder blades; +Y up, +Z away from the back |

Author props with their grip centred on the origin and the blade/handle along +Y, then parent them to the socket.

## Proportion variants

Parameters (`tools/cbase/params.py`, ranges enforced): `height` (absolute metres) and relative multipliers
`headSize, shoulderWidth, torsoWidth, torsoDepth, bellySize, armLength, legLength, handSize, footSize`.
Limb girth is derived from torso width/depth (not a free parameter).

A proportion change is a **character-creation** operation: the build regenerates the rest skeleton (joint
positions), the cage, the mesh, weights, socket placements and re-solves every clip (IK targets such as the test
handle are re-reached with the new arm lengths). Parts are never scaled independently of their joints.

### Create a variant
```bash
cat > my_variant.json <<'JSON'
{ "height": 1.62, "headSize": 1.1, "torsoWidth": 1.2, "bellySize": 1.8, "legLength": 0.9 }
JSON
.venv/bin/python tools/build.py build my_char --params my_variant.json --name "My character"
# inspect it: npm run viewer → select "my_char" (or ?char=my_char)
.venv/bin/python tools/build.py freeze my_char     # locks geometry + UVs (hashes recorded in the JSON)
```
The master and the stocky test variant are already frozen. `build` refuses to overwrite a frozen character —
make a new id instead.

### Freezing and UV stability
* The UV layout (`humanoid_uv` **v1**) is computed once for the template topology (angle-based unwrap, fixed
  seams, per-region texel density — face 2×, hands 1.5×, scalp 1.25× — oriented upright, packed with ≥8 px
  padding at 2048², 27 unique islands, **no stacked L/R islands**) and stored as data with a sha256.
* Every variant reuses the same layout by face-corner index; the build verifies the topology hash. A variant's UVs
  are therefore never regenerated. Changing the cage topology requires a new template/topology version and a
  new layout version (`tools/cbase/__init__.py`), which invalidates baked art by design.
* `freeze` records the geometry hash, UV sha256, GLB and .blend sha256. Texturing verifies all of them.

## Replace / apply a baked texture

**Pipeline (authoritative, keeps .blend in sync):**
```bash
.venv/bin/python tools/build.py texture stocky_test my_textured_char --image path/to/baked_basecolor.png
```
This opens the **frozen** source `.blend` (no regeneration), checks every part's geometry+UV hash, plugs the
image into `M_Body` base colour, exports `characters/my_textured_char/my_textured_char.glb` with the texture
embedded, saves a new `.blend`, copies the image to `textures/basecolor.png` and writes a JSON whose
`derivedFrom` points to the source. The texture must use the shared `humanoid_uv` v1 atlas (2048², sRGB,
glTF orientation: image row 0 = V 0).

**Viewer (quick look / demo):** Material → *Base-colour texture* file → *Save / export → Export GLB* (+ *Export
JSON*) → *Reload export in fresh viewer*. The viewer export (GLTFExporter) contains geometry, UVs, skin,
sockets, clips and the texture; viewer-only shaders (checker, coverage, exploded view) are never exported.

Re-open any saved character with `viewer/index.html?glb=<url>&config=<url>` or the file pickers; no browser
storage/session state is used.

## Projection references (for the future projection/bake tool)

`references/<id>/cameras.json` contains, per view (`front, back, left, right, front_three_quarter`):
image size (1536²), vertical FOV, near/far, position/target/up/quaternion, `matrixWorld`, `viewMatrix`,
`projectionMatrix` (column-major, glTF/three.js space) and the equivalent Blender camera. The pose is the
GLB bind pose (no clip). Files per view: beauty (neutral hemisphere + camera-aligned light, transparent
background), `masks/*_partid.png` (unlit, non-antialiased; colours in `partIdLegend`), `depth/`, `normal/`.

`coverage/` shows which surface the five views actually see (texture-space map + 3D views from unused
angles): magenta = not seen by any reference view, orange = grazing only. For the master: 2.7 % of UV texels
unseen, 6.7 % grazing-only; **the front view alone covers ~50 %** — a single front image is never full coverage.
The viewer has the same *Projection coverage* material mode.

No AI-image integration is included by design. A projector-only preview (custom shader) is not a finished
asset: bake it to the UV atlas first, then use `build.py texture`.

## Animation clips (baked, named glTF animations, 30 fps)

| clip | content |
|---|---|
| `idle` | 4 s loop: breathing, weight shift with planted feet, subtle head/arm motion |
| `reach_grip_handle` | right hand reaches the test handle, closes a fitted power grip (fingers + thumb searched for contact without penetration), holds, releases, returns |
| `press_button` | left index finger presses the test button (others curled), returns |
| `_qa_pose_cycle` | the 7 validation poses, each held 14 frames (markers in the JSON) |

Clips are authored as IK/FK recipes (`tools/cbase/clips.py`, `library.py`) and baked to rotation keys
(translation only on `pelvis`), so they play in any glTF runtime and bone lengths can never change.
The viewer's hand IK targets use the same roll-preserving two-bone solver; *Capture pose → clip* bakes the
current FK pose into an exportable clip.

## Validation (see `validation/REPORT.md`)

Each GLB is opened in a fresh browser context (viewer + only the GLB/JSON) and checked over every 2nd frame of
every clip (296 frames per character). Current result: **all checks pass for all three characters**, including

* 375 boundary vertices across 17 part pairs + all UV-seam duplicates: **max gap 0.0 m** in every frame; normals identical
* bone lengths constant to 2.5 µm (forearms/shins never shorten); sockets rigid in their bones (≤1e-15)
* helpers = half rotation within 0.035°
* palms face the body/down and thumbs sit on the radial (front) side, both hands
* grip: **0** hand vertices inside the handle, ~60 vertices within 4 mm (contact), socket exactly on the axis
* press: fingertip within ~1.1 mm of the button top at the contact frame
* viewer export (with texture) → reload in another fresh page passes the same structural/seam/bone checks

Screenshots: blank / checker / diagnostic texture in arms raised, deep elbow bend, hands near face, wrist
rotation + finger curl, torso twist, head turn and crouch, from two angles plus joint close-ups.

## Extending

* **Compatible meshes (clothing, accessories):** model over the A-pose, skin to the same skeleton (in Blender:
  Data Transfer → vertex groups from the nearest body part), keep weights ≤4 and normalised, export alongside.
  Rigid accessories just parent to a socket.
* **Another humanoid template** (e.g. chibi or creature): add a new cage/template version; skeleton names and
  clip recipes can be reused, UV layouts are per template.
* **Facial animation:** the head is a single rigid `head` bone today; the face topology (eye sockets, mouth line)
  leaves room for jaw/eyelid bones or blend shapes later.

## Known limitations

* Linear-blend skinning: very deep bends still compress somewhat (helpers keep volume, but there are no
  corrective shapes); the raised-arm armpit and crouched knee pit show typical LBS creases.
* 31k triangles is a hero-level master; no LODs yet (the cage can be subdivided once instead of twice for a
  ~7.9k-tri LOD, but that needs its own UV transfer).
* The test button prop is static (the press clip travels 6 mm "into" it); props are for validation only.
* The neck/sternal-notch junction and nape have visible soft creases under harsh lighting.
* Reference-view coverage is measured per texel with a 1.2 cm depth tolerance; it is a diagnostic, not a bake.
